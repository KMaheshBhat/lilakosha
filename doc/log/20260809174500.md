# RPGnet Ingestion Step - Design

* Created: 2026-08-09 17:45:00 IST
* Updated: 2026-08-11 15:30:00 IST
* Change Log

  * baseline design
  * established RPGnet/XenForo source shape and post extraction contract
  * validated parser against 2-row and 50-row probes
  * changed ingestion boundary to row-level reconciliation
  * defined Parquet ingestion as a replayable diff/patch against CDM state
  * removed diagnostic HTML output from production design
  * defined post-level source identity and replacement semantics
  * added extraction and preservation of RPGnet thread tags as thread-level source metadata

## Context / Background

`lemonilia/roleplaying-forums-raw` provides RPGnet's `Roleplay-By-Post Play Forum` as Parquet files containing scraped XenForo HTML pages.

The source is not structured as posts or threads. Each Parquet row is a complete HTML page. A row may contain a forum listing, a thread page containing multiple posts, a large thread containing hundreds or thousands of posts, or non-forum/error content.

The purpose of this step is to transform the source representation into the CDM representation established for asynchronous-session corpora:

```text
Thread → Document
Post   → NarrativeItem
```

The source Parquet row is therefore an acquisition container and reconciliation boundary, not the semantic unit of the resulting CDM.

The semantic unit extracted from a row is the post. A row may contain many posts belonging to the same thread. For each row, the extractor constructs the corresponding in-memory:

```text
Document[Thread]
    └── NarrativeItem[Post]
    └── NarrativeItem[Post]
    └── ...
```

The resulting in-memory representation is then reconciled immediately against the existing CDM state.

The Parquet source is therefore treated as a replayable diff/patch stream against the CDM:

```text
Parquet row
    → parse posts
    → construct in-memory Thread → Posts
    → locate existing Document
    → reconcile posts by source post identity
    → persist Document
```

The row is the unit at which source data is consumed and merged into CDM. The implementation must not accumulate the complete source corpus in memory before writing CDM state.

A subsequent acquisition may contain additional posts for an existing thread, the same posts again, or newer representations of previously observed posts. Re-running ingestion against the same acquisition must therefore be safe and deterministic.

The design is intentionally RPGnet/XenForo-specific. This step is allowed to understand the source structure directly; it does not attempt to introduce a generic forum abstraction.

## Entry Condition

The step expects:

* The RPGnet source files acquired under:
  `raw/lemonilia/roleplaying-forums-raw/`
* The currently acquired source files:

  * `RPGnet--roleplay-by-post-play-forum--part1.parquet`
  * `RPGnet--roleplay-by-post-play-forum--part2.parquet`
* Parquet records with the source schema:

```text
section_url: VARCHAR
contents:    VARCHAR
```

* `contents` containing XenForo HTML.
* A functioning CDM/ledger environment from which existing CDM records can be located through `LedgerIndex`.

The source acquisition is assumed to have completed successfully. Acquisition, source download integrity, and source discovery are outside this step.

The source shape has been inspected and established:

* 9,463 rows exist across the two files.
* The two files have identical schemas.
* A full-corpus exact-content duplicate scan found zero duplicate rows.
* Near-duplicate detection is not part of this ingestion step.
* Individual rows can be large, including approximately 33 MB of HTML.
* Individual rows can contain large numbers of posts.
* The source therefore cannot be treated as one-post-per-row or one-thread-per-row.
* Post identity and thread identity must be extracted from the HTML.

The parser has also been empirically exercised against representative source rows:

* a one-post sample;
* a fifty-post sample;
* the first two source rows;
* a 50-row source probe producing 1,702 post records.

The 50-row probe established the current extraction baseline: all 1,702 extracted posts had post IDs, thread identities, authors, timestamps, and content nodes present.

Thread tag extraction has also been validated against source rows containing the XenForo thread tag structure. The extracted values include both single-tag and multi-tag thread representations.

Diagnostic HTML files were used during parser development and inspection. They are not part of the production ingestion output.

## Exit Condition

A successful ingestion run will have:

* implemented as `step/ingest-lemonilia-rpgnet/__init__.py`;
* processed the acquired Parquet corpus row by row;
* ignored rows which contain no usable RPGnet post containers;
* extracted individual source posts from each useful row;
* retained the source identities required to reconcile those posts;
* represented each source thread encountered in a row as an in-memory CDM `Document`;
* represented each source post as a `NarrativeItem` within that document;
* located the corresponding existing CDM `Document` through `LedgerIndex`;
* created a new CDM `Document` where no corresponding source thread exists;
* minted and persisted a CDM document UUID only when required;
* reconciled extracted posts against the existing document by `post.id`;
* retained the representation with the newer `post.timestamp` when the same post occurs more than once;
* added newly encountered posts to the existing document;
* retained existing posts which are not present in the current source row;
* persisted the reconciled document after processing the row;
* preserved source thread, thread tags, post, author, and timestamp information required by subsequent refinement;
* normalized post content toward the established Markdown representation;
* preserved distinguishable OOC material as `reasoning` on the relevant original `ContentVariant`;
* left the resulting CDM state safe for subsequent refinement steps;
* remained safe to replay against the same acquired source.

The production step does not write extracted post HTML files. HTML artifacts are a parser-development diagnostic facility only and are not part of the ingestion contract.

## Core Shape

The processing order is:

1. Open the acquired Parquet files as one logical source corpus.
2. Read one source row.
3. Parse the row's `contents` as XenForo HTML.
4. Locate post containers.
5. If no post containers are present, treat the row as having no ingestible posts and continue.
6. Extract each post from the row.
7. Extract the source identity and metadata required for CDM reconciliation, including thread metadata and thread tags.
8. Construct an in-memory `Document[Thread]` containing the extracted `NarrativeItem[Post]` objects.
9. Use `LedgerIndex` to locate the CDM document corresponding to the source thread.
10. If no document exists:

    * mint a new CDM document UUID;
    * create the document;
    * register the source-thread-to-CDM-document relationship in `LedgerIndex`.
11. If a document exists, load the existing CDM document.
12. Reconcile each extracted `NarrativeItem` against the existing document using `post.id`.
13. When the post ID does not exist, add the post.
14. When the post ID already exists, compare `post.timestamp` and retain the newer representation.
15. Reconstruct/persist the resulting document.
16. Complete the row before moving to the next source row.
17. Continue until the logical Parquet corpus is exhausted.
18. Produce the normal pipeline completion/health information expected of an ingestion step.

The important boundary is:

```text
ONE PARQUET ROW
    ↓
POST EXTRACTION
    ↓
THREAD → POSTS
    ↓
LEDGER LOOKUP
    ↓
CDM RECONCILIATION
    ↓
CDM WRITE
    ↓
NEXT PARQUET ROW
```

The implementation must not accumulate all extracted posts from all 9,463 rows before reconciliation.

## Detailed Design

### 1. Source Row → Post Extraction

The Parquet row is an acquisition container. It is not itself a CDM record.

The extractor parses `contents` as HTML and searches for RPGnet/XenForo post containers.

The empirically established primary post container is:

```css
article.message.message--post
```

A row may contain zero, one, or many such containers.

The presence of post containers is the primary deterministic signal that a row contains ingestible post content. Rows without post containers are ignored by the ingestion step. This naturally excludes forum listings, error pages, notices, redirects, and other non-post pages without requiring those page types to become separate semantic classifications.

A source row may contain many posts belonging to the same thread. This is expected and is not treated as an ambiguity.

The extractor must therefore operate at:

```text
row → posts
```

rather than:

```text
row → thread
```

The thread relationship is derived from each post's source metadata.

The parser must process the complete HTML contents of the current row in memory. Observed row sizes make whole-corpus HTML accumulation inappropriate, but the observed row sizes do not require a streaming DOM implementation.

Diagnostic HTML output is not required by the production parser.

### 2. Post Identity

The source post ID is the primary identity used for CDM reconciliation.

The observed primary representation is:

```html
data-content="post-{post_id}"
```

with the observed alternative:

```html
id="js-post-{post_id}"
```

The extractor should use an explicit fallback sequence rather than depending on a single attribute.

Conceptually:

```text
post.id
    ← data-content="post-{id}"
    ← id="js-post-{id}"
    ← other validated source URL fallback, if present
```

The extracted value is the numeric RPGnet post ID.

The CDM/source identity is:

```text
rpgnet:post:<post_id>
```

This identity is stable across source pages and source reacquisitions and is therefore the identity used for replacement/deduplication.

Duplicate post IDs are not an architectural concern at the row level. Multiple posts in one row naturally belong to the same thread, and if the same post ID is encountered more than once, the same reconciliation rule applies: the newer timestamped representation wins.

### 3. Thread Identity

The thread is the semantic container represented by a CDM `Document`.

Thread identity is extracted from thread URLs embedded in the post's local HTML context.

Observed thread URL forms include:

```text
/index.php?threads/{slug}.{thread_id}/
```

and post-qualified forms such as:

```text
/index.php?threads/{slug}.{thread_id}/post-{post_id}
```

or the equivalent absolute URL.

The extractor must therefore not depend on one particular HTML element such as `meta[itemprop="parentItem"]`.

Thread identity extraction uses a fallback strategy over validated local thread URL candidates.

The minimum required source identity is:

```text
post.thread.id
```

The optional thread metadata is:

```text
post.thread.slug
post.thread.url
post.thread.tags
```

The CDM/source identity is:

```text
rpgnet:thread:<thread_id>
```

The thread ID is the identity used by `LedgerIndex` to locate the corresponding CDM `Document`.

Thread tags are extracted from the thread tag list present in the local XenForo HTML context.

The observed source representation is a XenForo `tagList` containing one or more `tagItem` elements. The extractor collects the textual value of each thread tag.

The resulting representation is:

```text
post.thread.tags: list[str]
```

Thread tags are source metadata. They are not normalized, clustered, classified, renamed, or mapped into a corpus-level taxonomy during ingestion.

The source tag values are retained as extracted because later corpus-level normalization and taxonomy work may intentionally collapse multiple source tags into a smaller semantic vocabulary. The original source tags therefore remain part of the source-faithful ingestion representation.

The presence of thread tags is not required for thread identity or post reconciliation.

Multiple posts in a row will normally have the same `thread.id`. This is expected and is represented directly as:

```text
Document[Thread]
    ├── NarrativeItem[Post 1]
    ├── NarrativeItem[Post 2]
    ├── NarrativeItem[Post 3]
    └── ...
```

The parser is not responsible for discovering whether a row contains multiple threads through an additional “thread grouping” phase. Each extracted post carries its thread identity, and the resulting post records are assembled into the corresponding in-memory document representation before ledger reconciliation.

### 4. Author Identity

The post author is extracted independently of post identity.

Observed source information includes:

```html
data-author="..."
data-user-id="..."
```

and user/profile links containing numeric RPGnet user IDs.

The minimum required representation is:

```text
post.author.id
post.author.label
```

Optional source author metadata may be retained where reliably available:

```text
post.author.*
```

The required CDM-facing source representation is therefore:

```text
rpgnet:author:<author_id>
```

where a stable source user ID is available.

The author display label is retained separately and must not be treated as the source identity.

Corpus-level identity resolution is outside this ingestion step. The ingestion step preserves RPGnet's source identity and label; later refinement may determine relationships to broader CDM person/character entities.

### 5. Timestamp

The source timestamp is extracted from the post-local `<time>` element.

The observed source representation provides a `datetime` attribute in ISO-8601 form, including timezone information.

The required field is:

```text
post.timestamp
```

The timestamp is retained as source metadata and is also the deterministic conflict-resolution value for post replacement.

When the same `post.id` is encountered more than once:

```text
existing.post.id == incoming.post.id
```

the representations are compared by:

```text
post.timestamp
```

and the newer representation wins.

The timestamp comparison is therefore semantic source reconciliation, not HTML-row deduplication.

Static HTML may contain indicators that a post was edited, but does not establish a reliable structured edit history. Ingestion therefore represents the latest/current source representation available in the acquired HTML. Historical revisions are not separate CDM `NarrativeItem` objects.

### 6. Post Content Extraction

Post content must be extracted through an explicit fallback hierarchy.

The extractor must not depend exclusively on:

```css
[itemprop="text"]
```

because representative RPGnet rows have demonstrated that valid post content exists even when that selector returns no nodes.

The observed source contains multiple content-container variations. They share the XenForo `bbWrapper` structure.

The content extraction strategy is therefore:

```text
post content
    ↓
preferred semantic content node, where present
    ↓
XenForo message-content/message-body structure
    ↓
.bbWrapper
```

The exact selector implementation must remain narrow to the current RPGnet/XenForo structures and should prefer the smallest node representing the actual post body rather than the complete post container.

The parser must distinguish:

```text
post HTML
```

from:

```text
post content HTML
```

The former is diagnostic/debugging material. The latter is the source representation which proceeds into content normalization.

The ingestion contract at this stage is only to obtain the correct source content HTML. Conversion into:

```text
NarrativeItem.content[ContentVariant]
```

is a subsequent representation concern within the ingestion implementation and must not be allowed to distort source extraction.

### 7. HTML → Markdown Normalization

The acquired RPGnet post content is XenForo-rendered HTML. The ingestion step must preserve this content as an identifiable, source-faithful post representation but does not perform the final HTML → Markdown transformation.

This is intentional. HTML → Markdown is expected to require iterative examination of real RPGnet content and repeated adjustment of deterministic conversion rules. Performing that transformation during ingestion would couple those iterations to the comparatively expensive Parquet → post extraction and CDM merge operation.

The ingestion boundary is therefore:

```text
RPGnet Parquet row
    ↓
XenForo HTML parsing
    ↓
Post
    ├── post.id
    ├── post.thread.*
    ├── post.author.*
    ├── post.timestamp
    └── post.content = source HTML content
    ↓
NarrativeItem
    ↓
CDM
```

`post.content` is retained as the source content representation. It must not be discarded or reduced to plain text merely because the final CDM presentation format has not yet been established.

The subsequent refinement step, currently envisaged as:

```text
refine-lemonilia-rpgnet-posts
```

will own the HTML → Markdown transformation. It can therefore be run repeatedly against the already-ingested CDM records as the conversion rules are developed and validated.

The refinement boundary is:

```text
CDM NarrativeItem
    ↓
source/original content
    ↓
RPGnet/XenForo HTML → Markdown
    ↓
normalized ContentVariant
```

The transformation is expected to be deterministic and RPGnet-specific. It should preserve meaningful content structure rather than reproduce XenForo presentation. The exact conversion rules remain to be established from inspection of the extracted corpus.

Known RPGnet/XenForo constructs that require explicit treatment include:

* `bbWrapper` content containers;
* headings;
* paragraphs and line breaks;
* links;
* images;
* quotes and quote attribution;
* spoiler-like constructs;
* code/preformatted content;
* HTML entities;
* rendered BBCode;
* XenForo-specific wrapper and presentation markup;
* other source constructs encountered during corpus inspection.

The extracted probe corpus has established that post content is not represented by a single universal HTML shape. At least two observed post-content structures contain the common `bbWrapper` content wrapper. The parser therefore uses fallback/NVL-style structural extraction rather than depending on one single content selector. The ingestion contract is the resulting `post.content`, not the particular selector used to obtain it.

The conversion must not be designed from the assumption that every post has identical markup. Source-specific structural variants should be handled by deterministic conversion rules and preserved where their semantic meaning can be identified.

Quotes remain part of the post's content. They should initially be converted to attributed Markdown blockquotes rather than extracted as separate CDM entities or relationships.

The transformation should preserve information wherever practical. Unsupported presentation styling may be lost, but source text, conversational structure, links, quotations, images, code/preformatted material, and other semantically meaningful constructs should not be discarded merely because their final Markdown representation has not yet been determined.

The initial ingestion therefore makes no claim that `post.content` is already normalized Markdown. It establishes a stable, replayable source representation from which Markdown normalization can subsequently be derived.

This also means that changes to HTML → Markdown rules do not require re-reading the RPGnet Parquet corpus or re-running post identity extraction. The refinement step can be rerun against the existing CDM representation until the normalization rules are satisfactory.

### 8. Quotes

XenForo quote blocks occur inside post content and may include attribution such as:

```text
Username said:
```

followed by quoted material.

Quotes are part of the post's content.

The initial representation preserves them as attributed quoted content, normally through Markdown blockquote semantics.

A quote does not become a separate `NarrativeItem`, `Document`, person, or relationship merely because it references another post.

Quote attribution is retained as content where available.

The ingestion step does not attempt to resolve the quoted material back to a source `post.id`.

### 9. OOC / IC Material

OOC material is useful human-to-human coordination surrounding the collaborative narrative.

The source does not provide a single authoritative OOC field. OOC signals may occur in:

* thread titles;
* post content;
* explicit OOC/IC markers;
* other textual source signals.

The ingestion step should preserve distinguishable OOC material rather than discard it.

Where deterministic extraction can identify OOC material, it is retained as:

```text
ContentVariant(name="original").reasoning
```

The initial implementation should remain conservative. It should not aggressively classify ambiguous prose as OOC.

The important ingestion property is preservation: material which may later be classified as reasoning must not be irreversibly discarded.

Improved reasoning/OOC classification is a subsequent refinement concern.

### 10. Row-Level Document Construction

After parsing the posts from one Parquet row, the extractor constructs an in-memory representation of the semantic document(s) represented by those posts.

The conceptual shape is:

```text
source row
    │
    ├── post
    │     ├── post.id
    │     ├── post.thread.id
    │     ├── post.thread.slug
    │     ├── post.thread.url
    │     ├── post.thread.tags
    │     ├── post.author.id
    │     ├── post.author.label
    │     ├── post.timestamp
    │     └── post.content
    │
    ├── post
    │     └── ...
    │
    └── ...
```

which becomes:

```text
Document[Thread]
    ├── NarrativeItem[Post]
    ├── NarrativeItem[Post]
    └── NarrativeItem[Post]
```

The Document is an in-memory semantic representation used for reconciliation.

The row itself is not persisted as a Document.

If the source row contains posts belonging to the same thread, those posts participate in the same in-memory `Document`.

The parser does not write the Document before reconciliation. The in-memory representation is first compared with the existing CDM state through `LedgerIndex`.

### 11. Ledger Lookup and Document Creation

For each source thread represented by the current row, the ingestion step derives:

```text
rpgnet:thread:<thread_id>
```

and queries `LedgerIndex`.

If the source thread has no existing CDM document:

1. mint a new CDM Document UUID;
2. construct the Document from the source thread metadata and extracted posts;
3. register the source-thread identity against the new document in `LedgerIndex`;
4. persist the document.

The relationship is therefore:

```text
rpgnet:thread:<thread_id>
        ↓
CDM Document UUID
```

The source thread ID is the stable identity. The CDM UUID is the local identity.

A later replay of the same source must resolve to the same CDM Document through the ledger rather than minting another document.

### 12. Row-Level Reconciliation / Diff-Patch

The Parquet source is treated as a sequence of patches against the CDM.

For each row:

```text
incoming Document[Thread]
        +
existing Document[Thread]
        ↓
reconciled Document[Thread]
```

The reconciliation unit is the `NarrativeItem`, identified by:

```text
rpgnet:post:<post_id>
```

For every incoming post:

```text
if post.id is absent from existing Document:
    add incoming NarrativeItem

if post.id exists:
    compare timestamps

    if incoming.timestamp > existing.timestamp:
        replace existing NarrativeItem
    else:
        retain existing NarrativeItem
```

Posts already present in the CDM but absent from the current source row are retained.

Thread-level metadata is reconciled independently of post presence.

When an incoming source row provides thread metadata such as slug, URL, or tags, that metadata may refresh the corresponding Document metadata.

Absence of thread tags in an incoming row must not be interpreted as an instruction to remove previously retained tags.

Thread identity remains authoritative:

```text
rpgnet:thread:<thread_id>
```

The operation is therefore a union plus deterministic replacement:

```text
existing posts
    ∪
incoming posts
```

with:

```text
same post.id
    → newer post.timestamp wins
```

This is the fundamental replayability mechanism.

A source row is not expected to contain a complete representation of a thread. It may contain only a page-sized subset of its posts. Therefore processing a row must never replace an entire existing Document merely because the current row contains fewer posts.

The row applies a patch to the existing Document.

### 13. Ordering

The semantic ordering of `NarrativeItem` objects follows the source post chronology.

`post.timestamp` is the authoritative source ordering value available from the extracted post representation.

When a Document is reconstructed after reconciliation, its NarrativeItems should therefore be ordered deterministically by source timestamp, with source post ID providing a deterministic secondary ordering where required.

The implementation must not use Parquet row order as semantic post order.

Parquet row order is acquisition order, not narrative order.

### 14. Document Metadata

Thread-level metadata may be encountered repeatedly across source rows.

The source fields:

```text
post.thread.id
post.thread.slug
post.thread.url
post.thread.tags
```

are source metadata.

The thread ID is authoritative for identity.

Thread slug, URL, and tags are descriptive metadata and may be refreshed when a newer or more complete source representation provides them.

Thread tags are retained as source values. The ingestion step does not normalize, deduplicate semantically, cluster, rename, or map tags into a corpus-level taxonomy.

The presence of tags is not required for thread identity or post reconciliation. A thread remains the same thread based on:

```text
rpgnet:thread:<thread_id>
```

regardless of whether tags are present in a particular source representation.

Document-level metadata must not cause an existing Document to be duplicated.

The source thread identity remains:

```text
rpgnet:thread:<thread_id>
```

regardless of which page or row supplied the metadata.

### 15. Large Source Rows

Observed source rows can be large, including approximately 33 MB of HTML, and can contain hundreds or thousands of posts.

This is not an architectural reason to redefine:

```text
thread → Document
post   → NarrativeItem
```

The processing boundary is nevertheless deliberately bounded at the Parquet row.

The implementation should:

* fetch/process one row at a time or in a bounded fetch batch;
* parse the complete HTML of the current row;
* extract posts from that row;
* reconcile them against CDM;
* persist the affected Document(s);
* release the row-level HTML and parsing structures before continuing.

The implementation must not accumulate all source HTML or all extracted posts across the corpus.

The current probe results demonstrate that row-level processing is practical for the acquired source. A 50-row probe produced 1,702 posts successfully while maintaining the intended operational resource profile.

If a specific very-large row causes an actual resource problem in production, that becomes an implementation optimization issue. It does not alter the semantic model.

### 16. Replayability and Idempotency

The ingestion step is explicitly designed to be replayable.

Given the same source acquisition:

```text
Parquet corpus
    → row
    → parse
    → reconcile
```

a second execution must converge on the same CDM state.

The critical identities are:

```text
rpgnet:thread:<thread_id>
rpgnet:post:<post_id>
```

Thread identity determines the target Document.

Post identity determines the target NarrativeItem.

Timestamp determines replacement when two representations of the same post are encountered.

Therefore:

```text
same thread + same post + same timestamp
    → no semantic change

same thread + same post + newer timestamp
    → replace post representation

same thread + new post
    → add post

new thread
    → create Document
```

Thread metadata, including tags, is descriptive rather than identity-bearing. Replaying a source representation with the same thread tags produces no semantic change. A newer or more complete source representation may refresh thread metadata without changing the thread identity.

A later acquisition can therefore be applied as another patch stream without requiring a clean rebuild of the CDM corpus.

### 17. Production Outputs and Diagnostics

The production ingestion step does not write individual HTML files.

During parser development, individual post HTML and content HTML files may be emitted as diagnostic artifacts to establish and inspect the source parsing contract.

Those files are not part of the production ingestion output because:

* the source HTML already exists in Parquet;
* CDM should contain the semantic representation rather than a second copy of the raw HTML;
* production output should not grow linearly with diagnostic parser artifacts.

Production output consists of the resulting CDM records, ledger relationships, and normal pipeline health/telemetry.

A diagnostic/probe mode may retain CSV and HTML outputs when validating parser behavior against representative source rows. Such output is explicitly outside the production step contract.

### 18. Failure and Resume Behavior

The row-level reconciliation boundary is also the restartability boundary.

The implementation must avoid treating the entire 9,463-row corpus as one transaction.

After successfully reconciling and persisting a row, its semantic effect exists in CDM.

If processing terminates after a later row, replaying the source from the beginning is safe because:

* existing thread identities resolve through `LedgerIndex`;
* existing post identities are reconciled by `post.id`;
* unchanged post representations do not produce semantic changes;
* newer representations replace older ones.

This allows restart from the beginning without requiring the source corpus to be partitioned into manually maintained checkpoints.

If the pipeline framework provides a stronger transaction/checkpoint mechanism, it may be used additionally, but correctness must not depend on a fragile assumption that the entire source corpus can be processed atomically.

## Open Items

There are no remaining architectural open items from the parser discovery work.

The following have been resolved into the detailed design:

* page classification is reduced to the deterministic presence/absence of usable post containers;
* thread identity uses post-local thread URL candidates with fallbacks rather than one authoritative HTML selector;
* thread tags are extracted from the XenForo thread tag list as source-faithful thread metadata;
* thread tags are preserved without normalization or corpus-level taxonomy mapping during ingestion;
* post identity uses explicit fallback extraction;
* author identity preserves RPGnet source identity and display label;
* content extraction uses a fallback hierarchy because `[itemprop="text"]` is not universal;
* quotes remain embedded post content;
* OOC material is preserved conservatively for later refinement;
* large rows are processed as bounded row-level units;
* source rows are treated as replayable patches against CDM;
* post reconciliation uses `post.id` with newer `post.timestamp` winning;
* thread metadata is reconciled independently of post presence;
* absence of thread tags in a source representation does not remove previously retained tags;
* production does not emit diagnostic HTML.

The remaining implementation choices are local implementation details unless empirical testing exposes a source behavior not covered by the established parser contract.
