## Background

There are report steps that were developed organically as need arose.  Not all, but a subset of these iterate over the CDM records, open them, intropsect them, update counters, and then report on the results.  All reports needs to be analyzed for such patterns, and a common `steps/report-cdm` should be developed with appropriate flags to enable/disable particular reporting types.

## Analysis

- **In-scope** (open and read CDM records):
  - `report-cdm-items`
  - `report-char-names`
  - `report-record-health`
  - `report-record-stats`
- **Out-of-scope** (inspect filenames only / filesystem metadata):
  - `report-cdm-records`

### In-scope reporting aspects

**`report-cdm-items`**
- Item kind frequency counts
- ContentVariant name frequencies (for unstructured variant-bearing items)
- Legacy scalar-content counts
- Missing / unexpected / malformed content flags
- Structured item counts (categorization category, sequence target)

**`report-char-names`**
- Per-record player name and gender
- Per-record bot name and gender

**`report-record-health`**
- Healthy vs defective record counts and percentages
- Source breakdown (by `source_identity`)
- Pipeline stage pass/check breakdown (annotation, categorization, bot detail, user info, safety axes, prose)
- Grammar conversion summary (total/converted/remaining turns, estimated compute)
- Per-record anomaly registry

**`report-record-stats`**
- Safety dial distributions (sexual, violence, toxicity axes)
- Primary genre mix
- Top thematic tags (top 25)
- Language distribution
- Conversation turn distribution (min, max, average, median, count buckets)

## Design

### Proposed Module: `steps/report-cdm/__init__.py`

A single unified telemetry step that consolidates all in-scope `report-*` logic behind boolean flags.  This removes duplicated record-iteration, Pydantic validation, and range-filtering code across four separate step directories.

#### Config Parameters

All flags live under `config["parameters"]`.  Range filtering applies globally to every enabled reporter.

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `report_items` | `bool` | `false` | Enable item-kind / content-shape / variant inventory (`report-cdm-items`) |
| `report_char_names` | `bool` | `false` | Enable character identity name & gender report (`report-char-names`) |
| `report_health` | `bool` | `false` | Enable record health audit (`report-record-health`) |
| `report_stats` | `bool` | `false` | Enable dataset distribution statistics (`report-record-stats`) |
| `report_turn_distribution` | `bool` | `false` | Enable turn-count distribution per record |
| `report_narrative_distribution` | `bool` | `false` | **NEW.** Enable narrative-item distribution per record |
| `report_hide_anomaly_details` | `bool` | `false` | Mute granular anomaly printing in health report |
| `report_breakdown` | `bool` | `false` | Enable pipeline stage breakdown in health report |
| `start_uuid` | `str \| None` | `None` | Lexical range floor (inclusive) |
| `stop_uuid` | `str \| None` | `None` | Lexical range ceiling (inclusive) |

If no `report_*` flag is set, the step logs a warning and exits without iterating records.

#### Shared Infrastructure

The module centralizes the boilerplate that is currently copy-pasted across every report step:

```python
from pathlib import Path
from typing import Any, Generator, Optional

from cdm.core import Document


def _resolve_records_dir(config: dict) -> Path:
    processed_vol = Path(config["volumes"]["processed"])
    return processed_vol / "cdm" / "records"


def _iter_record_files(
    records_dir: Path,
    start_uuid: Optional[str],
    stop_uuid: Optional[str],
) -> Generator[Path, None, None]:
    files = sorted(records_dir.glob("*.json"))
    for file_path in files:
        uuid = file_path.stem
        if start_uuid and uuid < start_uuid:
            continue
        if stop_uuid and uuid > stop_uuid:
            continue
        yield file_path


def _load_document(file_path: Path) -> tuple[Optional[Document], Optional[str]]:
    try:
        with open(file_path, "r", encoding="utf-8") as f:
            return Document.model_validate_json(f.read()), None
    except Exception as exc:
        return None, str(exc)
```

All reporters consume the same validated `Document` objects produced by `_load_document`.  This guarantees consistent error handling and eliminates redundant file-open / JSON-parse / Pydantic-validation cycles.  The main scan tracks parse-failure counts separately so the final report can expose an accurate evaluated-vs-skipped count.

#### Reporter Architecture

Each report type is implemented as a small accumulator class with `update(document)` and `render(total_records, source_counts)`.  Only reporters that actually carry breakdown data implement a dedicated breakdown-rendering method; there is no shared `render_breakdown()` interface.

```python
class _ItemReporter:
    def update(self, document: Document) -> None: ...
    def render(self, total_records: int, source_counts: dict[str, int]) -> None: ...


class _CharNameReporter:
    def update(self, document: Document) -> None: ...
    def render(self) -> None: ...


class _HealthReporter:
    def __init__(self, report_hide_anomaly_details: bool): ...
    def update(self, document: Document) -> None: ...
    def render(
        self,
        total_records: int,
        source_counts: dict[str, int],
    ) -> None: ...
    # Owns its own breakdown rendering because it is the only reporter
    # that currently has breakdown data.


class _StatsReporter:
    def update(self, document: Document) -> None: ...
    def render(self, total_records: int, source_counts: dict[str, int]) -> None: ...


class _TurnDistributionReporter:
    def update(self, document: Document) -> None: ...
    def render(self, total_records: int, source_counts: dict[str, int]) -> None: ...


class _NarrativeDistributionReporter:
    def update(self, document: Document) -> None: ...
    def render(self, total_records: int, source_counts: dict[str, int]) -> None: ...
```

#### Variance of Denominator

Health stage percentages can use different denominators: some stages are meaningful only for a specific source subset, while others apply to the whole corpus.  This behavior is G1-specific opinion, not generic machinery, so it is codified as a named constant rather than a configurable parameter.

```python
G1_HEALTH_DENOMINATORS = {
    "refine-cdm-language": None,                        # global
    "refine-cdm-html-to-markdown": "lemonilia/roleplaying-forums-raw",
    "refine-pippa-characters": "PygmalionAI/PIPPA",
    "refine-pippa-safety-dials": "PygmalionAI/PIPPA",
    "refine-pippa-genre-theme": "PygmalionAI/PIPPA",
    "refine-pippa-grammar": "PygmalionAI/PIPPA",
}
```

The main loop maintains `source_counts` as corpus-level telemetry.  `_HealthReporter.render()` receives `total_records` and `source_counts`, looks up each stage's target source in `G1_HEALTH_DENOMINATORS`, and uses that source's count as the stage denominator when it is not `None`.  This keeps the source accounting in one place and prevents the denominator logic from becoming a silent YAML tuning knob.

#### Main Loop

```python
def run(config: dict) -> None:
    params = config.get("parameters", {})

    records_dir = _resolve_records_dir(config)
    if not records_dir.exists():
        logger.error("Records directory not found: %s", records_dir)
        return

    start_uuid = params.get("start_uuid")
    stop_uuid = params.get("stop_uuid")
    file_iter = _iter_record_files(records_dir, start_uuid, stop_uuid)

    reporters = _build_reporters(params)
    if not reporters:
        logger.warning("No report-* flags enabled; nothing to do.")
        return

    logger.info("Running unified CDM report across records...")

    total_records = 0
    skipped_records = 0
    source_counts: dict[str, int] = {}

    for file_path in tqdm(file_iter, desc="Scanning CDM Records"):
        document, parse_error = _load_document(file_path)
        if document is None:
            skipped_records += 1
            logger.debug("Skipping %s: %s", file_path.name, parse_error)
            continue

        total_records += 1
        source_identity = (
            (document.meta.source or {}).get("source_identity")
            or (document.meta.source or {}).get("source")
            or "unknown"
        )
        source_counts[source_identity] = source_counts.get(source_identity, 0) + 1

        for reporter in reporters:
            reporter.update(document)

    for reporter in reporters:
        reporter.render(total_records, source_counts)

    if skipped_records:
        logger.warning(
            "Skipped %d records due to parse/validation failures.",
            skipped_records,
        )
```

#### Backward Compatibility

All existing `pipeline/*.yml` files that reference the legacy `report-*` steps will be migrated to call the unified `report-cdm` step with the appropriate flag combinations.  The actual YAML edits and deprecation of old step directories are out of scope for this proposal.

#### New Feature: Narrative Distribution

This report uses exactly the same implementation pattern as the Turn Distribution.  It reads the pre-computed `meta.stats.narrative_count` value and renders the same bucketed distribution style.

**Per-Record Metric Collected**

| Metric | Source | Description |
|--------|--------|-------------|
| `narrative_count` | `meta.stats.narrative_count` | Number of pure narrative items in the record |

**Corpus-Level Distribution Output**

The Narrative Distribution section renders the same bucketed distribution style as Turn Distribution:

- **Narrative Count per Record** — min, max, average, median, and count buckets.

No new abstraction is introduced; the narrative reporter reuses the existing distribution logic sibling-wise with the turn reporter.

## Implementation Deviations

- **Operator-friendly list-based configuration**: Replaced the individual boolean flags (`report_items`, `report_char_names`, `report_health`, `report_stats`, `report_turn_distribution`, `report_narrative_distribution`) with a single ordered `report_sections` list.  This lets operators control both the enabled sections and their execution/reporting order from one parameter.

  ```yaml
  parameters:
      report_sections:
        - health
        - stats
        - items
        - char_names
  ```

- **Legacy flag fallback retained**: The step still honors the original boolean flags when `report_sections` is absent, ensuring existing pipelines do not break during the transition.

- **Section names do not match flag names verbatim**: The list uses operator-facing names (`stats` instead of `report_stats`, `char_names` instead of `report_char_names`) to reduce YAML noise and improve readability.

- **Narrative distribution consolidated into `stats`**: Rather than exposing `narratives` as a standalone report section, narrative item distribution is now rendered as a sub-section inside the `stats` report, immediately before the Conversation Turn Distribution.  This reduces output fragmentation while preserving the data.

- **Ordered execution and rendering**: Reporters are instantiated and executed in the exact order declared in `report_sections`, and their output is rendered in that same order.  The design doc assumed a fixed factory order; this change makes reporting order an explicit, configurable property.

## Implementation Summary

- **Unified step module**: Implemented `steps/report-cdm/__init__.py` consolidating four legacy report steps (`report-cdm-items`, `report-char-names`, `report-record-health`, `report-record-stats`) behind a single entry point.

- **Removed legacy steps**: Deleted `steps/report-cdm-items/`, `steps/report-char-names/`, `steps/report-record-health/`, and `steps/report-record-stats/` directories after migrating all in-scope pipeline files.

- **Kept out-of-scope step**: `steps/report-cdm-records/` remains because it operates on filesystem metadata / LedgerIndex rather than opening CDM records, which was explicitly excluded from the unified design.

- **Renamed module**: The unified step directory was ultimately named `report-cdm` (instead of the initially proposed `cdm-report`) to better match existing naming conventions.

- **Migrated pipeline files**: Updated all `pipeline/35-report-*.yml` files to use the unified `report-cdm` step with `report_sections` lists.  Legacy test file `pipeline/20260814090000-report-legacy-test.yml` was intentionally left untouched for comparison.

- **Consolidated narrative distribution**: Rather than a standalone reporter, `narrative_count` distribution is rendered inside the `stats` section, immediately before Conversation Turn Distribution.
