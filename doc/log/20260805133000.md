# 2026-08-05 the content variant, the sequence, and the book on the shelf

Two weeks ago I wrote about LilaKosha becoming operational — about a system that encounters failures and mostly knows what to do about them.  That has held steady.  The difference is that what the system now knows how to do has grown in several concrete directions.

The corpus is now 16,833 records (16,832 PIPPA + 1 Gutenberg).  The work since the last post has largely been about hardening the CDM's content model, standardizing the pipeline's naming, and bringing a second, structurally different source into the fold.

## ContentVariant: one model, many forms

The most significant change to the CDM itself was the introduction of `ContentVariant`.  The original Turn model had gradually accumulated purpose-specific fields: `prose`, `original_prose`, `prose_revision_comments` on NarrativeItem, `thought` on TurnItem, and a bare `content: str` across WorldItem, CharacterItem, and SummaryItem.  That worked while the data still closely resembled the PIPPA traces that originally motivated the schema.  It becomes awkward once the CDM is expected to hold other kinds of documents — or, more immediately, once those fields need to coexist with multiple named transformations of the same text.

`ContentVariant` replaces all of those with a single representation: an item's `content` is now a `List[ContentVariant]`, where each variant carries a `name` (e.g. `original`, `refine-pippa-grammar`, `character-refined`), the variant `text`, and an optional `annotation`.  The same mechanism applies uniformly to worlds, characters, summaries, narratives, and turns.

During refinement I can keep the forms that are useful.  When producing a particular generation dataset I can select the variants I want and discard the rest without having to reinterpret a collection of special-purpose fields.

The health checker (`calculate_health`) and stats reporter (`calculate_stats`) in `cdm/meta.py` were updated to operate against this new structure.  Health validation now inspects variant names directly — e.g. a grammar-refined turn is considered complete only when both `original` and `refine-pippa-grammar` variants are present.  Stats now report an aggregate `word_count` summed across every variant on every item.  All serialization paths use `by_alias=True` so that alias-aligned field names flow through cleanly to disk and back.

Two follow-up refinements landed shortly after:

- **Extra dynamic attributes.**  `ContentVariant` now carries `model_config = ConfigDict(extra="allow")`, so individual variants can carry provider-specific or step-specific metadata that doesn't need to be part of the formal schema but should still round-trip.
- **`InferenceBudgetExhausted` exception.**  The `refine-pippa-grammar` and `refine-pippa-genre-theme` steps now support a `max_inference_budget` binding parameter.  When the budget is consumed the exception cleanly unwinds the nested turn/record loops, flushes a summary, and exits gracefully — so a local inference window can be cut short without corrupting state.

## PIPPA naming: from generic to explicit

The pipeline steps were previously named generically — `refine-characters`, `refine-grammar`, `scalpel-corrupt-cdm`, and so on.  With Gutenberg ingestion now entering the picture (see below), that generic scheme no longer scales: a name like `refine-grammar` is ambiguous when you might someday refine prose from multiple sources.

All steps were renamed to the `refine-pippa-*` / `scalpel-pippa-*` convention, and the corresponding pipeline manifests were renamed accordingly (`30-refine.yml` → `30-refine-pippa.yml`, `20-ingest.yml` → `20-ingest-pippa.yml`, and so forth).  README.md, doc/design.md, and doc/operator.md were all updated to reflect the new, source-explicit naming and the multi-source pipeline directory layout.

One naming slip — a singular `refine-pippa-character` variant — was caught and corrected to `refine-pippa-characters`, and a one-off migration pass (`migrate-pippa-2`) rewrote the incorrect key across all 16,832 existing records.

The health report now also reports a per-step `breakdown` dictionary and applies PIPPA-specific validation rules when `source_identity == 'PygmalionAI/PIPPA'`.

## Gutenberg #62: the first literary ingestion

The second structural difference between a PIPPA conversation trace and a Gutenberg novel is that the former is a *sequence of turns* while the latter is a *sequence of paragraphs arranged into chapters*.  Both need to be representable without special-casing either one.

`SequenceItem` received a new `data: Dict[str, Any]` field for extensible, sequence-level metadata.  The `ingest-gutenberg-62` step downloads "A Princess of Mars" (Project Gutenberg #62), locates the standard boundary markers, parses foreword and chapter headers, normalizes soft-hyphenated wrapped lines, extracts standalone footnotes, and emits `NarrativeItem`s — each carrying an `original` ContentVariant — grouped under per-chapter `SequenceItem`s and a root book-level `SequenceItem`.  The first Gutenberg record (UUID `019fcc23-4821-...`) now sits at the end of the ledger, and the record-count rose from 16,832 to 16,833.

`ingest-pippa` was updated in parallel so that it now emits a `SequenceItem` alongside the TurnItems during initial ingestion, giving every PIPPA session an ordered conversation timeline from the moment it lands.

## Recovering the whole timeline: a second scalpel

After the August 3 naming refactor, the eight re-ingested records from the July 31 corruption incident needed their refinement annotations re-validated.  The `scalpel-cdm-record` step (a general-purpose surgical purge that deletes individual record files and atomically unregisters them from the ledger mapping) was available for targeted range or UUID-list operations.  For the smoke test run, the `report-documentitems` inspection pass confirmed the full corpus: 16,833 documents, 951,528 items, 0 malformed variant-bearing items.

The PIPPA sequence migration — which backfilled a `SequenceItem` for every existing conversation document — was a one-pass operation that touched 16,832 records.  Once the corpus had absorbed it, the temporary migration step was removed and the two pipeline manifests that orchestrated it were archived into `doc/log/` as immutable execution records.

## What the system did, and what it still doesn't

A PIPPA smoke test was run from a clean workspace: fresh ingestion of 5 records, full refinement sweep (characters → safety dials → genre/theme → grammar), a health audit, a stat report, and a scalpel correction pass targeting the one record that failed validation — all followed by a re-run that correctly picked up only the cleared work.  The pipeline completed without operator intervention beyond the initial manifest selection.

The local rate-limit retry logic (exponential backoff, configurable `retry_on_rate_limit` per service, provider-requested `retry-after` delay, 2480-second cap) and the RPM throttle's `finally`-block placement — discussed in the previous post as they were being built — have now been validated under real provider cooldowns and require no further changes.

Some of the things I could still build remain on the shelf: CRPO signals, judge models, rating systems, corpus-wide semantic evaluation passes.  None of them are required to get Generation 1 out.

## Remaining work

- **Theme clustering and relabeling** — the corpus-level semantic pass mentioned in the previous post is still the most obvious piece of engineering work.  The CDM is in a shape that can hold the results, but the clustering itself has not been implemented.
* **Gutenberg refinement** — the first Gutenberg record now provides a new refinement surface: the evolved safety-dials, genre/theme, and character refinements need to be applied to the literary corpus, with the resulting patterns and metadata mined out as the Gutenberg pipeline matures.
- **Gutenberg scaling** — "A Princess of Mars" was ingested as a proof of concept.  The remaining selected works still need to be run through the same ingestion path.

In summary, this fortnight the CDM gained a unified content model (`ContentVariant` with extensible `data` on `SequenceItem`), the pipeline gained source-explicit naming, and a second document type entered the corpus as a first-class CDM citizen.  The system broke in a few ordinary ways — a naming typo, a smoke test that returned invalid JSON from the local provider, a naming slip that needed correcting — and increasingly the system just knew what to do about them.

There is still plenty to do, but the machinery for doing it is no longer experimental.
