# 2026-07-31 resilience, recovery, and letting the pipeline become boring

Two weeks ago I wrote about LilaKosha settling into a rhythm.  That seems to have been accurate.

Since then, most of the work has not been particularly glamorous. The corpus has continued through refinement, providers have been swapped around as their quotas and availability changed, ranges have been started and stopped, and the local machine has spent a considerable amount of time doing grammar conversion.

The project is beginning to look less like a collection of experiments and more like an operation.

The corpus is now 16,832 records. The remaining work is no longer about proving that the refinement pipeline can process a few thousand records. It is about getting the whole corpus through the machinery reliably, recovering when something goes wrong, and making sure that the records themselves remain useful as the project evolves.

That has shifted where I have been spending my time.

One small example was rate limiting. The inference layer originally treated a rate-limit response much like any other failure. That is not particularly useful when the thing on the other side is telling you, quite explicitly, to wait.  The OpenAI-compatible inference implementation now has configurable rate-limit retries, reads the provider's requested delay when available, and uses exponential backoff for subsequent attempts. The backoff cap is deliberately quite high because some of the remote providers can impose surprisingly long cooldown periods. There is not much point in making the pipeline fail just because the provider needs a little more time.

There was another less obvious problem in the refinement steps themselves. The RPM throttle was being updated only after a successful inference call. That meant that a failed request could bypass the pacing mechanism and immediately lead to another request. A timeout or validation failure could therefore produce a burst of requests precisely when the provider was already unhappy.  The throttle is now updated in a `finally` block. Whether the inference succeeds or fails, the pipeline has to respect the configured pacing.

Neither change adds any intelligence to LilaKosha. They simply make it better at continuing to run.

That distinction is becoming increasingly important.

The most visible example came this week when I discovered that eight CDM records had been corrupted. The cause was not particularly mysterious: the records are written as individual JSON files, and an interrupted write can leave one of those files incomplete.  And they were getting interrupted because BESCOM has been sending "dirty" (read - fluctuating) power down the powerlines I had to shutdown the pipelines and not have them run overight.

This did not need any special recovery procedure, and only a scalpel operation.

The new scalpel step walks the CDM records, validates them against the actual `Document` model, and removes records that cannot be parsed. It also removes the corresponding entries from the ledger. The ledger update itself is done atomically, using the same general principle as the record storage: do not leave half of the system believing that a record exists while the other half says that it does not.

The eight records were purged, re-ingested, and put back through refinement.  The refinement pipeline on those eight records is happening as I write this, and should be done by end of the day (unless the powerlines start to act out).

This is probably the clearest sign yet that LilaKosha is becoming operational. The pipeline is now expected to encounter failures. The question is whether those failures can be handled as part of the system rather than becoming little archaeological expeditions every time something goes wrong.

The provider situation has also become more fluid.  The higher-cognition refinements continue to use remote capacity where it makes sense, particularly for characters, safety dials, and genre/theme work. Grammar conversion is different. It runs on every turn, and there are currently hundreds of thousands of turns to process. At this scale, a provider with an attractive request rate does not necessarily solve the problem if the workload itself is enormous.

The local Gemma4 12B has therefore remained an important part of the pipeline, and several of the later corpus ranges have simply been moved back to local processing when remote capacity became inconvenient or unavailable.  The good thing about this is that the pipeline does not particularly care.

The provider is becoming an implementation detail rather than a fundamental property of the dataset.  The other significant change this week was in the CDM itself.

Next, I have enhanced the CDM design with `ContentVariant`, which will be implemented (and the corpus adhoc-migrated), before getting into the two items I mentioned in my last post:

- Gutenberg ingestion and corpus design
- Theme clustering and relabeling

The original Turn model had gradually accumulated fields for different kinds of content: prose, thought, original prose, revision comments, and so on. That worked while the model was close to the shape of the PIPPA data that originally motivated it. It becomes increasingly awkward once the CDM is expected to hold other kinds of documents and increasingly elaborate transformation histories.

ContentVariant replaces those purpose-specific fields with a common representation for unstructured content.  An item can now contain an `original`, a `normalized`, a `generated`, or another named variant, with optional annotation alongside it. The same mechanism applies to worlds, characters, summaries, narratives, and turns.

It also makes an important distinction clearer: the record itself is the durable thing. A particular textual representation is just one form that the record happens to contain at a particular point in its lifecycle.  That should make later pruning and flattening much simpler. During refinement I can keep the forms that are useful. When producing a particular generation dataset, I can select the variants I want and discard the rest without having to reinterpret a collection of special-purpose fields.

In other words, the CDM is starting to become less about representing the current pipeline and more about representing the things the pipeline does to documents.

There are still plenty of interesting things I could build. CRPO signals, judge models, rating systems, corpus-wide evaluation passes, more elaborate semantic refinement, and so on. Some of them will probably become useful later.   But they are still not required to get Generation 1 out.

The work over these two weeks has instead been mostly about ingestion, refinement, resilience, recovery, and keeping the CDM in a shape that can absorb the next kind of data.

The pipeline is running. The corpus is growing. Bad records can now be cut out and recreated. Providers can be changed without changing the corpus. Refinement can continue through failures rather than stopping at the first unhappy request. And the document model is becoming less tied to the dataset that happened to come first.

There is still plenty to do.

Theme clustering remains one of the more obvious corpus-level engineering tasks. Gutenberg ingestion is still waiting in the wings, and I expect it to be a useful test of whether the CDM really is as document-oriented as I now claim it is. The current refinement backlog also needs to finish, including the eight records that were just re-ingested after the corruption incident.

In summary, this fortnight, the system broke in a few ordinary ways, and increasingly the system knew what to do about it.
